# 长任务循环故障诊断（loop-failure-diagnosis）

> 支撑决策号：D093（任务收口与子代理任务边界）· 性质：实战故障诊断（内部教训，非外部调研）
> 取证日期：2026-09-15 · 取证方式：全库会话日志扫描与逐会话字段比对

## 一、故障现象

子代理在 reasoning（思考）块中反复输出筹备性元话语（「让我执行」「即将发出」「好的，继续」类），不产生有效动作，任务永不收敛。用户侧表现为「AI 反复说要执行但一直不执行」。

## 二、取证数据

| 指标 | 观测值 |
|---|---|
| 单个异常会话规模 | turn 488、step 6204、957 轮 |
| 自动续行次数 | 418 次 `<goal_round>` |
| 上下文裁剪 | 335 次 compaction（每次裁 2,600 至 4,900 token） |
| 工具调用 | 1,961 次 |
| 子代理是否调用过 goal 工具 | 否（续行来自机制层，非子代理自建） |
| 全库异常大会话（10MB 以上） | 47 个共享同一 goal |
| 异常会话身份 | 全部 preset=dsh-codepunk、origin=subagent、depth=1、seeded=true |
| 项目分布 | 46/65 集中于同一工程；其余项目零星 |

## 三、根因链

1. 目标语义本身是**循环型**（「收敛到连续 5 轮达标」——需反复迭代直到条件成立）
2. 该目标被交给**子代理承载**（而非主会话分段驱动）
3. 子代理持续接收 goal 自动续行
4. 任务永不收敛，跑到数百轮
5. 上下文被裁剪数百次，早期 persona 与输出纪律被稀释失效
6. 模型在极端长程下 reasoning 退化，输出筹备性元话语循环
7. 失败后重派新子代理 → 复制整个过程（47 个会话）

## 四、为什么提示词不能根治

| 原因 | 依据 |
|---|---|
| 循环在 reasoning 层 | 提示词主要约束输出格式，对思考退化作用有限 |
| 约束被裁剪稀释 | 数百次 compaction 后，早期写入的 persona 规则已不在上下文 |
| 根因是任务粒度与续行机制 | 与措辞无关 |

## 五、修复（D093，已落地）

| 层 | 措施 | 落点 |
|---|---|---|
| 预设层 | R15：子代理 MUST NOT 承载循环型目标；此类目标由主会话按轮驱动，每轮只派单次可收敛任务（50 轮内） | SKILL R15 |
| 预设层 | 任务收口纪律 5 条：思考层禁复述执行意图、单席 100 轮上限、大目标 MUST 拆分、禁无限续行空转、连续 2 轮无产出即上报 | references/output-discipline.md |
| 预设层 | persona 约束：主 persona 与 11 岗位同步加 D093 | agent.cordis.yml |
| 使用侧 | 循环型目标不派子代理；重写或停用已产生的循环 goal；控制 goal 续行轮次 | 需部署方执行 |

## 六、派单前自检（run-lead，MUST）

1. 目标含循环语义？（收敛 N 轮 / 反复迭代 / 直到达标）
2. 若是 → 拆为单次任务，由主会话按轮驱动
3. 单次任务是否 50 轮内可收敛？否 → 继续拆

## 七、复现要点（供未来验证）

- 构造一个含「收敛到连续 N 轮」语义的目标，直接派给子代理
- 预期（修复后）：run-lead 按 R15 拒绝承载该目标，改为拆分为单次可收敛任务
- 若观察到子代理仍接该目标并跑过 100 轮，说明 R15 未被遵守，需检查 persona 生效状态（改 agent.cordis.yml 后须重启 DSH）
